# MindDuet Chess 开发复盘：从可运行棋盘到个性化学习闭环

> 截止日期：2026-08-07。本文根据本仓库提交历史、实现代码和自动化测试整理，是 MindDuet 后续系统设计的实践基线，而不是产品宣传材料。

## 结论先行

MindDuet Chess 已经证明了一条可运行的路径：把用户的真实行为保留为证据，用确定性工具判断事实，用 AI 把事实转化为教学语言和新训练题，再以之后的表现修正用户画像。

它的价值不在于“做了一个会下棋的软件”，也不在于“接入了大模型”。真正完成的验证是：

```text
真实行为 -> 可验证分析 -> 可追溯诊断 -> 个性化干预
        -> 后续作答/对局 -> 更新画像与下一次干预
```

这正是 MindDuet 面向数学、语言或其他复杂学习场景时必须保留的主干。象棋提供了清楚的规则和强引擎，因此适合先把这条链路走通；数学系统应复用这套职责边界，而不是复刻象棋界面或棋类算法。

## 已形成的系统

当前系统由三种角色协作，且不能混淆。

| 角色 | 当前实现 | 负责的事实 | 不应承担的职责 |
| --- | --- | --- | --- |
| 规则与引擎 | `XiangqiGame`、Pikafish | 合法走法、轮次、胜负、最佳着、评分、主变 | 教学语言、人格化判断、长期学习结论 |
| AI 教练 | DeepSeek Chat | 基于给定证据解释错因、编写提示、提出训练草案 | 篡改引擎结论、编造变化、直接判定棋局真伪 |
| 个人数据库 | SQLite / `GameDatabase` | 对局、分析、悔棋、画像、训练、复习记录 | 根据一次事件给用户下永久结论 |

因此，当前运行链路是：

```text
对局或专项训练
  -> 保存局面、着法、用时、悔棋与结果
  -> Pikafish 异步计算并保存评分/主变
  -> 本地规则生成诊断标签和画像
  -> DeepSeek 依据最小必要证据解释或提出题目草案
  -> XiangqiGame + Pikafish 再次验题
  -> 题目入个人题库，作答结果进入间隔复习与画像
```

## 关键问题、采取的改进与经验

### 1. 只有棋盘和引擎，不能构成学习系统

早期系统能下棋，却无法回答“我为什么总在这里犯错”“我练过之后是否改善”。因此加入了对局、走法、局面、思考时间、评分、主变和训练结果的持久化。经验是：**先保存原始证据，再做任何智能推断**。如果没有原始证据，未来再好的模型也无法追溯或纠正历史判断。

### 2. 悔棋不等于错误不存在

把悔棋直接从棋谱删除，会让系统失去最有价值的一类信号：用户是在落子后才发现问题。现在 `undo_events` 独立保存被撤销着法和后续分析，统计与训练会把它视为待提前识别的错误模式。专项训练中，错误着也可被推演、再悔棋重算，且不会重复计错。

经验是：**行为回滚与学习证据保存必须分离**。这条原则可直接迁移到数学中的改答案、删除草稿、查看提示和放弃作答。

### 3. LLM 适合教学设计，不适合做事实裁判

AI 可以写出自然的解释和貌似合理的棋题，但无法保证局面合法、变化成立或答案唯一。项目因此坚持“先有引擎证据，再让 AI 解释”；AI 原创题也必须经历：JSON 结构检查、`XiangqiGame` 合法性校验、Pikafish 重算最佳着和主变，才可入库。

经验是：**模型输出应当是候选和语言层，不是最终真相**。在数学里，对应的验证器将是标准答案、符号计算、步骤规则、题目元数据和教师审核。

### 4. 个性化不是重复展示旧错题

历史错题只能回答“当时为什么错”。用户需要的是“换一个局面后还会不会犯同类错误”。系统先从 Pikafish 主变中生成画像变式，再让 DeepSeek 按弱项、训练计划和最近主题提出原创局面。两类新题都保留来源标记，不会伪装成历史事实。

经验是：训练必须区分三种目标：

1. 回忆：重看真实错误；
2. 迁移：处理同类但变化后的局面；
3. 保持：在延迟后再次正确作答。

### 5. 每次出题都上传全部数据既昂贵又不必要

当前出题上下文只包含总体训练统计、当前训练计划、能力维度摘要、最多三条高置信证据和最近六个 AI 题主题。它不会上传全部棋谱、所有聊天或数据库内容。

经验是：先在本地把“数据”压缩为可解释的“学习状态”，再发送给模型。这样减少成本、降低隐私风险，也让模型更聚焦。未来应为画像加入版本号，使系统只在画像发生实质变化时改变出题策略。

### 6. 后台生成要有库存策略，而不是无条件调用

最初的后台预取解决了等待问题，但每次打开训练都发请求，会造成题库膨胀和 API 浪费。现在采用低水位策略：未练过的 AI 原创题少于三道时，后台只补一题；打开训练、完成 AI 题、悔棋记录新尝试或从库存切题后都会检查一次。点击“AI 出新题”先消费已验证库存，只有没有可用库存时才直接请求。

经验是：AI 请求需要像缓存一样管理，至少应有目标库存、去重键、主题冷却时间、失败退避和触发条件，而不是把“调用模型”当成普通 UI 点击事件。

### 7. 可读的展示本身是学习功能

早期的最后一步提示线和紧凑按钮影响理解与操作。之后改为高对比圆环和箭头、变化逐手回放、中文棋谱、两列稳定按钮网格，以及错误着后的惩罚线。AI 的坐标着法也被限制为中文棋谱。

经验是：对学习系统而言，界面并非只负责美观。用户是否看得懂“错误如何发生”和“下一步该怎么算”，决定了反馈能否变成能力。

### 8. 异步边界必须明确

Pikafish 搜索、DeepSeek 请求和数据库回填都可能晚于用户下一次操作。系统用请求 ID 匹配响应，将引擎分析、错误着复盘和 AI 出题分别保存在待处理队列中，避免旧响应覆盖新局面。所有引擎和网络工作保持在 UI 线程之外的异步流程。

经验是：任何学习产品中，题目切换、撤销、重试和迟到 AI 响应都必须是首等状态，而不是异常分支。

## 已知限制与不应过度承诺的部分

- Pikafish 的“最佳着”不等于人类学习者唯一可以接受的答案。后续要支持近似等价着、难度自适应和容错判分。
- AI 原创题目前按完全相同的局面编码去重，尚未做战术结构相似度去重。
- 画像仍是可解释的规则型统计，不是经过大规模验证的知识追踪模型；它应被视为需要后续证据检验的假设。
- 整局 AI 复盘依赖外部服务可用性。无模型时必须持续提供本地引擎事实和明确降级提示。
- 目前的效果证明主要是系统行为与自动化测试，不是“训练已显著提高棋力”的因果证明。要证明教育效果，需要训练前后对照、同类错误复发率和延迟测验数据。

## 验证与工程纪律

当前回归测试覆盖训练记录、悔棋、训练 UI、引擎变化回放、多用户画像和 JSON 响应解析。每次涉及规则、数据库或训练逻辑的改动，都应至少运行完整 `ctest`；涉及界面的改动，还应启动隔离测试窗口检查文字、按钮和棋盘状态。

需要长期坚持的工程规则：

- 规则只在 `XiangqiGame` 中实现，UI 与 AI 不复制局部判定逻辑；
- 引擎走法和模型候选都必须先验证；
- 数据库 schema 改动必须兼容现有用户数据；
- API 密钥、用户数据库、引擎文件、截图和构建产物不进入 Git；
- 模型请求只发送完成任务所需的最小上下文；
- 每条重要诊断都应能回到具体局面、着法、评分或用户行为证据。

## 对 MindDuet 的迁移含义

象棋与数学的对应不在于题型相同，而在于学习系统的结构相同。

| MindDuet Chess | MindDuet Math |
| --- | --- |
| 棋局局面与着法 | 题目、步骤、草稿与最终答案 |
| 合法走法和 Pikafish | 标准答案、SymPy、评分规则、步骤验证器 |
| 评分损失与错着 | 得分损失、概念错误、运算错误、条件遗漏 |
| 悔棋、提示、思考时间 | 改答案、查看提示、草稿停顿、信心变化 |
| 诊断标签和训练计划 | 知识点掌握、错误类型、学习计划 |
| 错题、画像变式、AI 原创题 | 真实错题、参数变式、AI 题目草案 |
| 后续对局表现 | 延迟测验、同类题迁移、课堂作业表现 |

最需要迁移的是以下机制：

1. **证据链**：每个诊断都能追溯到作答和判定依据。
2. **验证链**：模型写解释和草案，符号工具、规则和教师决定正确性。
3. **干预链**：根据画像选择错题回顾、变式训练或原创题，而不是随机刷题。
4. **反馈链**：之后的真实表现决定原画像是否成立，不让系统自说自话。
5. **人机协作链**：学习者和教师可查看、纠正、质疑系统，而非被黑箱标签支配。

## MindDuet 最终系统的建议路线

### 阶段 A：数学 MVP，先建立可信数据闭环

选择一个小专题，例如函数单调性与最值。准备教师审核的知识点树、错误标签、标准答案和题目元数据。先完成：学生作答、结构化记录、客观/符号判题、教师查看和基础错题训练。此阶段不依赖 AI 也必须成立。

### 阶段 B：可解释画像和训练编排

按知识点、错误模式、用时、提示依赖、改答行为和置信度建立画像。每个画像维度都要写明证据数、置信度、趋势和可证伪的假设。训练包应混合历史错题、受控变式和延迟复习，并记录训练后是否迁移。

### 阶段 C：受控 AI 教练与出题

让模型基于压缩画像生成分层提示、解释和题目草案。题目须经过数学验证器和教师抽检；模型回答必须引用给定步骤证据，不能替代判题器。使用低水位题库存、主题去重和画像版本号控制调用成本。

### 阶段 D：教师工作台与小规模实证

教师应可查看原始作答、系统诊断、AI 理由、训练安排和学生后续表现，并能修正标签与题目。小规模试验中重点比较：同类错误复发率、延迟测验、提示依赖下降、教师修正率和学生主观负担，而非只统计题量或聊天次数。

### 阶段 E：在证据足够后再引入统计模型

当积累了可靠的作答与效果数据，再考虑知识追踪、项目反应理论、多臂老虎机或强化学习推荐。它们应优化已经被验证的目标，例如长期保持和迁移成功率，而不是在没有可信标签的数据上盲目训练。

## 建议的北极星指标

MindDuet 不应以“生成了多少题”或“调用了多少次模型”为成功指标。更有意义的是：

- 同类错误在后续真实任务中的复发率是否下降；
- 延迟后仍能独立完成的比例是否上升；
- 用户对提示的依赖是否下降；
- 系统诊断被教师或用户纠正的比例是否下降；
- AI 原创题是否真正带来迁移，而不是只提高熟题正确率；
- 每个有效学习增益所需要的模型调用成本是否可接受。

## 后续优先级

1. 为 AI 题加入结构相似度去重、主题冷却与难度分层。
2. 支持多个近似等价答案的引擎判分，减少“不是唯一首选即错误”的误伤。
3. 用真实后续对局量化训练效果，并把效果回写到画像置信度。
4. 建立画像版本、出题策略版本和题目质量反馈，形成可审计的实验记录。
5. 启动 MindDuet Math 的小专题 MVP，优先复用证据、验证、画像、训练与复测的框架，而不是先追求大而全的 AI 对话功能。

## 最终判断

MindDuet Chess 的成功标准不是棋盘功能齐全，而是证明了一个严谨的学习产品原则：**AI 的创造性应该被放在可验证的教学设计中，人的长期进步必须由真实行为证据来衡量。**

只要 MindDuet 后续仍坚持“事实可验证、诊断可追溯、干预可检验、模型受约束、用户可参与修正”，它就有机会从象棋原型发展成真正可信的个性化学习系统。
